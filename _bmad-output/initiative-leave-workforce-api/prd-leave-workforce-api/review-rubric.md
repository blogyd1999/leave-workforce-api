# PRD Quality Review — Leave and Workforce Management API

## Overall verdict
This is a strong PRD for its stakes. It has a clear thesis (the system enforces the rules, so figures cannot drift), honest known limitations, and nearly every FR carries testable consequences. The balance arithmetic is consistent and all approved decisions in §10.1 are traceable to the FRs. The main risks are a handful of response-code contradictions against SEC-11, one real omission (no credential reset or unlock path, so a forgotten password on the sole Administrator is unrecoverable), and an increment order (§8.3) that puts Administrator endpoints before authentication. These can be fixed in a short pass, and none blocks architecture.

Dimension summary: Decision-readiness strong; Substance over theater strong; Strategic coherence strong; Done-ness clarity adequate; Scope honesty adequate; Downstream usability adequate; Shape fit adequate.

## Decision-readiness — strong
Decisions are stated as decisions in §10.1 (AP-1 to AP-9, Q1 to Q8), each with a "Where applied" column. Limitations L-1 to L-7 name what was given up. For example, L-1 says the Top-Most Person, the bootstrapped Administrator and any not-yet-assigned Employee cannot take leave, with "no Administrator override and no delegation". §10.3 separates recommended defaults from approved decisions, and §10.4 says plainly that "No unresolved question blocks architecture, UX or ticketing." The open questions are real: Q-A is jurisdiction and retention, Q-B is Top-Most Person policy.

### Findings
- **low** Two question-numbering schemes (§10.1, §10.3, §10.4) — Q1 to Q10 refer to an "earlier review" that is not in the PRD, and the open items use Q-A to Q-C. A reader of the PRD alone cannot tell what Q5 asked, and Q4/Q7 versus Q-A overlap in topic. *Fix:* give the approved items descriptive IDs (as with AP-n) or add a one-line question text to each Q row in §10.1.
- **low** "idempotent" in Q8 vs FR-27 (§10.1 Q8, §4.1 FR-27) — Q8 says "idempotent Bootstrap Operation", but FR-27 specifies a repeat run is refused and recorded as an attempt. The effect is idempotent, but the response is not a success. *Fix:* say "repeat-safe" or "refuses repeats without change".

## Substance over theater — strong
Personas are four named roles and each drives rules (the Manager only sees Available, the Administrator cannot decide, the Top-Most Person case produces L-1). There is no innovation or vision theater. The Vision (§1) is specific: it names "overlap other leave or exceeds the balance". The performance NFR has a number and scale (§6, 500 ms p95, 200 Employees). A few NFRs are adjectival (see Done-ness).

### Findings
- **low** Adjectival NFRs (§6) — "Maintainability: ... splittable later without rework" and "API quality: consistent errors" have no checkable bound. SM-7 ("usable by a front-end developer without reading the code") is likewise subjective. *Fix:* name a testable proxy (for example, a single documented error shape; module dependency rule checked in CI) or move them explicitly to architecture.

## Strategic coherence — strong
The thesis is "enforced rules, not drift", and the metrics validate it: SM-2 (zero overlap/negative-balance cases, including concurrent ones), SM-3 (authorization matrix with SEC-11 codes), and SM-5 (bootstrap safety). Counter-metrics SM-C1 and SM-C2 are named and tied to SM-6 and SM-1. The scope is coherent: a problem-solving MVP with a narrow path.

### Findings
- **low** SM-1 over-claims (§9) — "Validates FR-1 to FR-22, FR-27", but UJ-1 to UJ-6 never exercise FR-5, FR-6, FR-8 or FR-9. SM-6 is a process practice, not a measure. The performance NFR has no associated metric. *Fix:* narrow SM-1's "Validates" list to what the journeys touch, or add the matrix (SM-3) for the rest. Add a p95 check if the NFR is meant to be gated.

## Done-ness clarity — adequate
Most FRs have concrete, testable consequences (FR-14, FR-15, FR-19, FR-27 are exemplary: atomicity, concurrency, exact refusal conditions). Balance arithmetic checks out: UJ-1 gives Total 12, Reserved 5 and Available 7 after submit. Approval gives Total 7, Reserved 0 and Available 7, which matches FR-19 ("Total decreases... Reserved decreases by the same amount; Available is unchanged"). FR-12 and AP-8 are consistent. The weakness is the response-code policy: SEC-11 sets a rule, but several FRs diverge from it. Some security and API behaviours are also left unmeasurable.

### Findings
- **high** FR-21 contradicts SEC-11's tie-break (§4.5 FR-21, §5 SEC-11) — FR-21 says "A caller with no Direct Reports receives 403 on the decision endpoints" and also that a non-Direct-Manager Manager gets 404. An ordinary Employee deciding a colleague's request is a caller with no reports, and is also not entitled to know the request exists. SEC-11 says "Where both apply, 404 wins", so the outcome is 403 or 404 depending on which bullet is read. The same ambiguity applies to a Manager deciding their own request: FR-19 and FR-21 say 403, but that Manager is "not the Direct Manager of the request's owner" (the 404 bullet). It resolves only because the owner can read the request. *Fix:* order the rules explicitly in FR-21: (1) caller cannot read the request, so 404; (2) caller can read it (owner, Administrator) but cannot decide, so 403; (3) otherwise a non-Manager with no entitlement gets 404. State this once and reference it from FR-19 and FR-20.
- **medium** FR-16 and FR-24 vs SEC-11 (§4.4 FR-16, §4.6 FR-24) — FR-16 says "any other caller receives 404" for cancel. An Administrator and the Direct Manager can read the request (FR-17), so under SEC-11 ("deciding a request they are allowed to read" gets 403) they should get 403. FR-24 says an Administrator cannot cancel but gives no code. SM-3 will test against SEC-11 and fail on FR-16 as written. *Fix:* align FR-16 and FR-24 to the same three-way rule as FR-21.
- **medium** FR-17 and FR-23 conflict on former-Manager visibility (§4.4 FR-17, §4.6 FR-23) — FR-17 returns 404 for another Employee's request "unless the caller is an Administrator or that Employee's Direct Manager" (current). FR-23's `[ASSUMPTION]` says a former Manager keeps visibility of requests they decided. Under FR-17 that former Manager gets 404 on the single-request lookup while FR-23 lists it. *Fix:* extend FR-17's exception to "the request's decider", or drop the FR-23 assumption.
- **medium** Initial balance state undefined (§4.3 FR-11, §4.4 FR-14, §4.1 FR-1) — FR-11 sets Total "when no balance exists", but nothing says whether a new Account has a zero balance or no balance. FR-14 does not say what happens when no balance exists, and FR-13 does not say what an Employee sees. *Fix:* state that an Account starts with Total 0 (or that submission and view are refused with a specific reason until a balance is set).
- **medium** Removing a Direct Manager is not specified (§4.1 FR-3) — "set or change" is covered. Whether an Administrator can clear a manager (making someone a Top-Most Person) is not stated. If so, the Employee's Pending requests would be orphaned (FR-3 moves them only to "the new Direct Manager"). *Fix:* either forbid clearing while Pending requests exist, or say what happens to them.
- **medium** Throttling and token lifetimes are not testable (§4.2 FR-7, §5 SEC-3, SEC-5) — "throttling or temporary lockout", "approximately 15 minutes" and "Thresholds are decided in architecture" give no bound, no refusal code for a locked-out caller, and no Refresh Token lifetime ("longer-lived"). SM-3 and the stories cannot assert them. *Fix:* give indicative values (for example, lockout after 5 failures for 15 minutes; refresh 7 days) marked as defaults, plus the response for a throttled call (and confirm it does not reveal email existence).
- **low** FR-19 does not carry AP-1's 404 (§4.5 FR-19, §10.1 AP-1) — AP-1 lists FR-19 as applying the 404 rule. FR-19 states only "A Manager cannot approve their own request (403)" and relies on FR-21. FR-20 has no response codes. *Fix:* cross-reference FR-21 in both.
- **low** FR-6 ambiguity and no own-profile read (§4.1 FR-6) — "403 on the list" for non-Administrators, yet "A Manager can view the name and email of their Direct Reports"; it is unclear whether that is a separate endpoint. There is no way for an Employee to read their own Account, role or Direct Manager, but "any other Account by a non-Administrator returns 404". *Fix:* add a "view own Account" consequence and name the Manager's report list as its own operation.
- **low** Paging and error shape unspecified (§4.6 FR-22, §4.7 FR-26, §6 API quality) — paging is required, but there is no default or maximum page size; "consistent errors" has no shape. *Fix:* set a default and max page size, and state one error envelope.
- **low** FR-4 reactivation wording (§4.1 FR-4) — "any Direct Manager link removed in the meantime" does not say what removes a link while an Account is deactivated (deactivating a manager is refused while they have reports). *Fix:* clarify which link this refers to (the deactivated Employee's own manager?) or delete the clause.
- **low** Audit actor for system-driven cancellation and SM-4 wording (§4.7 FR-25, §9 SM-4) — Deactivation cancels Pending requests (FR-4), but FR-25 does not say who the actor is. SM-4 says "Every state-changing action listed in FR-25", but FR-25 includes login success and failure. *Fix:* name the actor as the deactivating Administrator, and say "every event listed".

## Scope honesty — adequate
§7 Non-Goals is thorough and does real work (no editing, no cancelling an Approved request, no Administrator override). L-1 to L-7 are candid. Assumptions are inline and indexed. The one significant silent omission is credential recovery.

### Findings
- **high** No credential reset, unlock or forgotten-password path, and not listed as a non-goal (§4.1, §4.2, §7, §10.2) — FR-2 and L-6 cover only the initial credential, and FR-10 requires the current password. SEC-5 introduces lockout, but nothing unlocks an Account. SEC-12 says an Administrator "cannot read credentials", but does not say whether they can set one. If the only (bootstrapped) Administrator forgets the password, the system is unrecoverable except by database access, and the Bootstrap Operation refuses to run (FR-27). *Fix:* either add an FR for an Administrator-initiated credential reset (the Account returns to must-change state, audited, never revealing the value), or add an explicit non-goal and limitation (L-8) and say how the last Administrator is recovered.
- **low** Health and OpenAPI endpoints are referenced but not specified (§5 SEC-7, §6 API quality, §9 SM-7) — "login, refresh and health" are exempt from authentication, but no FR defines the health endpoint. Whether the OpenAPI document is exposed (and to whom) is also unspecified. *Fix:* one line in §6 for each.

## Downstream usability — adequate
This PRD feeds architecture and ticketing, so this dimension matters. IDs are contiguous and unique, and cross-references resolve (see Mechanical notes). Each UJ names a protagonist with inline context. The US table (§4.8) gives ticketing a direct FR mapping. The risk is in the sequencing and a few coverage gaps.

### Findings
- **medium** §8.3 increment order has dependency inversions (§8.3, §9 SM-6) — Increment 1 delivers "Administrator endpoints" before increment 2 delivers login, but SEC-7 requires authentication on every endpoint. FR-2 gating ("can call only the change-credential... operations") needs FR-10 from increment 2. FR-1, FR-3 and FR-27 all require Audit Records, but audit (FR-25 write path) is only placed in increment 7 ("Audit read endpoint and hardening pass"). SM-6 says each increment must be "demonstrable before the next starts", which increment 1 cannot satisfy. *Fix:* put login and token issuance, plus the audit write mechanism, in or before increment 1, and keep only the audit read endpoint in 7. Or mark the order as indicative given that "final slicing is a ticketing step".
- **low** Stories do not cover every FR (§4.8) — FR-24 (Administrator visibility) and FR-25 (record audit events) appear in no US. FR-24 is only reachable via "any user" US-14, which lists neither it nor FR-24. *Fix:* add a story for each, or map FR-24 into US-4.
- **low** FR-27 placed out of numeric order (§4.1) — FR-27 sits after FR-6 in §4.1, and §8.1 and SM-1 must cite "FR-1 to FR-6, FR-27" and "FR-1 to FR-22, FR-27". Because the placement is deliberate, the §4.1 description points to it, and §8.1 and the §4.8 US-15 row make it findable, the harm is small. A story or ticket extractor working from numeric ranges would miss it, which is an easy mistake. *Fix:* keep it, but add a note under §4.8 or §0 ("FR-27 is numbered out of order; it belongs to 4.1"), or renumber so ranges close.
- **low** Glossary drift (see Mechanical notes).

## Shape fit — adequate
Chain-top and internal-tool shaped. A capability-spec layout with six UJs, 15 user stories and 27 FRs is somewhat heavy for a single-organisation API, but because the PRD feeds architecture and ticketing, the formality is defensible. The UJs are useful because they carry the edge cases (UJ-2's 404, UJ-3's reassignment, UJ-6's repeat bootstrap).

### Findings
- **low** Three overlapping layers (§2.3, §4, §4.8) — UJs, FR consequences and the US table restate the same behaviour three times. Each added layer is a place for drift (see the FR-17 and FR-23 divergence). The front-end developer is a JTBD (§2.1) with no UJ or FR, only SM-7. *Fix:* keep the US table as a pure index, and either drop the front-end developer JTBD or label it as a constraint on SM-7.

## Mechanical notes

**ID continuity.** FR-1 to FR-27 are contiguous and unique (FR-27 is physically in §4.1). UJ-1 to UJ-6, SEC-1 to SEC-21, SM-1 to SM-7 plus SM-C1 and SM-C2, US-1 to US-15, L-1 to L-7 and AP-1 to AP-9 are contiguous. The Q-ids are non-contiguous by design (Q1, Q2, Q4, Q6 to Q8 in §10.1; Q3, Q5, Q9, Q10 in §10.3), and Q-A to Q-C are separate. All cross-references resolve: FR-22 (§3), FR-13 (§4.5), SEC-2, SEC-5, SEC-11, L-1, L-2, §10.1 Q4/Q7, §10.3 Q10, and every "Realizes UJ-n" and every US to FR mapping. SM-1 "FR-1 to FR-22, FR-27" omits FR-23 to FR-26, which SM-4 and SM-3 partly cover.

**FR-27 placement.** Judged low-harm; see Downstream usability.

**Assumptions Index roundtrip.** Clean. All eight inline tags (§3 Manager, FR-2, FR-4, FR-17, FR-18, FR-23, SEC-18, §6 performance) appear in §11. The three index lines that have no inline tag are the Q3/Q5/Q9/Q10 defaults (which live in §10.3) and "Brief A1 to A4" (which live in the brief); these are acceptable but cannot be checked inside the PRD. Format is inconsistent: some tags are bare `[ASSUMPTION]` (§3 Manager, FR-18, FR-23, SEC-18) and others carry text. SEC-18 is a requirement tagged as an assumption, and it may be better as a plain requirement. I did not re-verify A1 to A4 against the brief.

**Response codes (SEC-11 vs FRs).** Consistent: FR-1, FR-6 (list), FR-26 (403, administrative endpoint exists openly), FR-7 (401 generic), FR-17 (404), FR-19 own request (403 readable), FR-21 Administrator and owner (403). Inconsistent: FR-21's "no Direct Reports, 403" vs the 404 tie-break, FR-16 "any other caller receives 404" vs readers (Administrator, Direct Manager), and FR-24 (no code). FR-3, FR-4, FR-5, FR-11, FR-12 and FR-24 omit the Administrator-only 403 that SEC-11 implies. See the Done-ness findings.

**Balance arithmetic.** Consistent. UJ-1: 12, then 5 Reserved (7 available), then approved with Total 7 and Reserved 0. FR-14, FR-16, FR-19 and FR-20 all keep Available equal to Total minus Reserved. FR-12 and AP-8 prevent Total from going below Reserved. FR-4 releases Reservations atomically. The only gap is the missing initial state (see Done-ness).

**§10.1 "Where applied" check.** AP-2, AP-3, AP-4, AP-5, AP-6, AP-7, AP-8, AP-9, Q1, Q2, Q4, Q6 (via AP-8) and Q7 are reflected where stated. AP-1 is reflected in SEC-11, FR-6, FR-17 and FR-21, but only partly in FR-16 (it conflicts with SEC-11 for readers) and FR-19 (no 404 or reference to FR-21). Q8 is reflected in FR-27 and UJ-6, except for the "idempotent" wording.

**Glossary drift.** Low impact overall. (1) "Operator" (US-15) and "developer-operator" (UJ-6) are not glossary terms. (2) "decider" (FR-3, FR-17, UJ-1) is not defined. (3) "credential" (FR-2, FR-27) vs "password" (FR-10, SEC-1, SEC-2) are used interchangeably, so FR-10 "Change own password" and the "change-credential" operation in FR-2 read as different operations. (4) Lowercase "request" or "requests" and "balance" are used as shorthand throughout for Leave Request and Leave Balance. (5) "manager" in lowercase (FR-3 "The manager must be an active Account") when "Direct Manager" is meant. (6) "admin" or "administrative endpoint" (SEC-11) vs Administrator. (7) "Any user" (US-5, US-14) is not an actor in the glossary. (8) "status history" (FR-22) vs "request history" vs the Audit Record (partly handled in the glossary).

**UJ protagonists.** All six are named (Asha, Ravi, Meera, Asha, Priya, Karan) with context inline. UJ-4 reuses Asha, which is fine.

**Required sections.** All present for the stakes and product type. There are no `[NOTE FOR PM]` callouts, but §10.3 and §10.4 do the same job. Open-item density is moderate (8 assumptions, 4 default confirmations, 3 open questions, 7 limitations) and appropriate for a low-stakes learning project.
